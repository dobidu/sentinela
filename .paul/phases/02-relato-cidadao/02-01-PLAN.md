<objective>
## Goal
Abrir o primeiro caminho de escrita do Sentinela, só no banco e sem UI: um cidadão anônimo, com a publishable key, consegue (1) subir uma foto para um bucket privado e (2) registrar um relato via RPC `submit_report`. O hash do token é calculado no servidor, o município é resolvido pelo ponto, há rate limit e todo status fica num histórico. Junto: João Pessoa e Cabedelo com limites oficiais do IBGE em produção, keep-alive para o free tier não pausar e o drift da CLI no Dependabot resolvido.

## Purpose
É a base da feature 1 (relato do cidadão). 02-02 (formulário) e 02-03 (offline) só consomem esse contrato. Fazer a escrita primeiro no banco, com pgTAP, mantém a regra das duas barreiras (privilégios + RLS): `anon` ganha exatamente as funções listadas e nada além. O keep-alive vem antes porque a pausa de 2026-10-01 já quebrou o CD uma vez.

## Output
- Migration `report_write_path` (municípios reais, histórico de status append-only, `updated_at`, bucket + policy de storage com teto, RPCs `submit_report` (idempotente), `resolve_municipality`, `ping`, `can_upload_report_photo`)
- `supabase/seed.sql` sem os retângulos sintéticos de JP/Cabedelo (agora vêm da migration)
- pgTAP: novo `report_write.test.sql`; `rls.test.sql` com allowlist explícita de funções de `anon`
- `src/lib/database.types.ts` regenerado
- `.github/workflows/keep-alive.yml` (cron a cada 3 dias + manual)
- `.github/dependabot.yml` ignorando `supabase` (bump manual sincronizado)
- README: contrato de escrita anônima, keep-alive, procedimento de bump da CLI

```gherkin
Given role anon, um objeto recém-enviado em `report-photos/<uuid>.webp` e um token UUID v4

Then retorna o id do relato criado com status 'pending'
And `reporter_token_hash` = sha256 do token (o token não é gravado em nenhum lugar)
And `municipality_id` é resolvido pelo ponto, não informado pelo cliente
And `report_status_event` tem 1 linha (null → pending, changed_by null)
```

## AC-2b: Reenvio idempotente (retry da fila offline)
```gherkin
Given um relato já criado com photo_path X pelo token T
When o mesmo token T chama `submit_report` de novo com o mesmo photo_path X (resposta anterior perdida na rede)
Then retorna o id do relato existente, sem criar relato nem evento novo e sem consumir rate limit
And se um token diferente usa o photo_path X, é recusado (foto já usada)
```

## AC-3: Relato anônimo inválido é recusado (fail-closed)
```gherkin
Given role anon
When chama `submit_report` com: ponto fora de todos os municípios; foto inexistente no bucket; foto já usada por outro relato; foto enviada há mais de 1h; path fora do padrão; descrição > 500 chars; token que não é UUID
Then cada caso é recusado com SQLSTATE específico e nenhum relato nem evento é criado
<!-- audit-added -->
And token nil (`00000000-…`) ou UUID que não seja v4 é recusado
And lon/lat não finitos ou fora de faixa são recusados antes de qualquer consulta espacial
```

<!-- audit-added -->
## AC-3b: Contrato de erro consumível pelo cliente
```gherkin
Given qualquer recusa de `submit_report` via PostgREST
When o cliente recebe a resposta
Then o HTTP status distingue as classes: 429 (rate limit: retentar depois), 404 (foto não encontrada: refazer upload e retentar), 409 (foto já usada por outro token: permanente), 422 (validação/fora do município: permanente)
And os códigos são SQLSTATE `PTnnn` do PostgREST, documentados numa tabela no README (código, HTTP, retentável sim/não, ação do cliente)
And nenhuma mensagem de erro contém o token, o hash ou a coordenada enviada
```

## AC-4: Rate limit
```gherkin
Given um mesmo token
When envia mais de 5 relatos em 1h (ou mais de 20 em 24h)
Then o relato excedente é recusado com SQLSTATE 'PT429' (HTTP 429)
And outro token no mesmo período não é afetado
And há um teto global por município (200/h) que recusa com o mesmo código, como disjuntor contra rotação de token
<!-- audit-added -->
And chamadas concorrentes do mesmo token não furam o limite (contagem serializada por advisory lock transacional do hash; teto global serializado por município)
```

<!-- audit-added -->
## AC-4b: Upload anônimo com teto
```gherkin
Given o bucket `report-photos`
When anon tenta enviar além de 300 objetos na última hora ou além de 3000 objetos no total
Then o INSERT em storage é recusado pela policy (fail-closed: upload para; não há custo nem estouro silencioso do free tier)
And o teto é verificado por função SECURITY DEFINER `can_upload_report_photo()`, porque anon não lê `storage.objects`
```

## AC-5: Superfície de anon é exatamente a planejada
```gherkin
Given o catálogo do banco
When se listam os privilégios de anon
Then anon executa exatamente `submit_report`, `resolve_municipality`, `ping` e `can_upload_report_photo` (comparação por assinatura `regprocedure`, sem overloads), e nenhuma outra função de public <!-- audit-modified -->
And anon continua sem nenhum privilégio de tabela em public (não lê nem insere `report` direto)
And em storage, anon só faz INSERT no bucket `report-photos` com nome `^[0-9a-f-]{36}\.(webp|jpg)$`: não lê, não lista, não sobrescreve, não apaga
And o bucket é privado, com file_size_limit 2 MB e MIME só image/webp e image/jpeg
And `resolve_municipality` devolve só id e nome (nunca o boundary)
And advisors de segurança continuam sem warning
```

## AC-6: Histórico de status
```gherkin
Given um relato existente
When o status muda por qualquer caminho (inclusive service_role)
Then `report_status_event` registra from → to, timestamp e changed_by (auth.uid() ou null)
And `report.updated_at` é atualizado
And `report_status_event` não pode ser apagado em cascata (RESTRICT) e tem RLS de leitura por município igual às demais tabelas
<!-- audit-added -->
And cada evento tem `source` ('citizen' na criação via RPC, 'staff' quando há auth.uid(), 'system' caso contrário), e o evento de origem fica distinguível do service_role
And UPDATE sem mudança real de status não gera evento
And `report_status_event` é append-only: UPDATE, DELETE e TRUNCATE são recusados por trigger, inclusive para service_role/postgres
```
