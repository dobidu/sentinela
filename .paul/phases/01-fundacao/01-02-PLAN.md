<objective>
## Goal
Versionar o schema do banco como migrations Supabase: PostGIS, as 6 entidades do modelo de dados com escopo de município em toda tabela, RLS habilitado e restritivo, tipos TypeScript gerados — tudo provado por testes pgTAP rodando localmente e num job de CI.

## Purpose
Toda fase seguinte (relato, agregação, dashboard) grava ou lê essas tabelas. As decisões "multi-município desde o dia 1" e a política LGPD (coordenada exata só para agente/vigilância, anonimato do relator) precisam estar no schema e nas policies antes da primeira linha de UI — retrofit de tenancy e de RLS é caro e arriscado.

## Output
- Projeto Supabase local (`supabase/`) com 2 migrations (schema, RLS) e seed sintético
- Testes pgTAP de schema e RLS em `supabase/tests/database/`
- `src/lib/database.types.ts` gerado do schema
- Job `database` no CI: sobe Postgres, aplica migrations, roda pgTAP, lint do schema, checa drift dos tipos
</objective>

<decisions>
## Decisões fixadas no planejamento (2026-09-24, confirmadas pelo usuário)
- `reporter_token` NÃO é armazenado em claro: coluna `reporter_token_hash` (SHA-256, `bytea` 32 bytes). Deduplicação usa o hash.
- Role `anon`: zero acesso a qualquer tabela neste plano. Caminho de inserção de relato entra na fase 2.
- `admin`, `agent`, `surveillance`: todos restritos ao próprio `municipality_id`. Operação cross-município só via `service_role` (jobs/scripts).

## Refinamentos do modelo de dados (derivados de PROJECT.md, sem mudar semântica)
- `Report.photo_url` → `photo_path` (caminho no bucket privado; URL assinada é gerada na leitura — URL persistida contradiz "bucket privado + URL assinada").
- `User` → tabela `profile` (1:1 com `auth.users`), pois identidade vive no Supabase Auth.
- `municipality_id` em TODAS as tabelas de domínio (report, risk_area, alert, inspection, profile), não só por relação — requisito para policies simples e índices por tenant.
</decisions>

## AC-1: Banco local reproduzível
```gherkin
Given Docker rodando e `pnpm install` feito
When rodo `pnpm db:start` seguido de `pnpm db:reset`
Then o Postgres local sobe com a extensão PostGIS habilitada
And as migrations aplicam do zero sem erro, seguidas do seed

```

## AC-2: Schema cobre o modelo de dados com tenancy
```gherkin
Given as migrations aplicadas
When inspeciono o schema `public`
Then existem as tabelas municipality, profile, report, risk_area, alert, inspection
And toda tabela exceto municipality tem `municipality_id NOT NULL` com FK para municipality
And `report.geom` é `geometry(Point, 4326)`, `risk_area.geom` é `geometry(Polygon, 4326)`, `municipality.boundary` é `geometry(MultiPolygon, 4326)`, todas com índice GiST
And status/role/tipo de criadouro/risk_level/outcome são enums Postgres (valores inválidos rejeitados)
And `report` não tem coluna de token em claro — apenas `reporter_token_hash bytea` com CHECK de 32 bytes
```

## AC-3: Integridade espacial
```gherkin
Given um município com boundary definido no seed
When insiro (como service_role) um report cujo ponto está fora do boundary do seu municipality_id
Then o insert é rejeitado com erro explícito
And um report com SRID diferente de 4326 também é rejeitado
And um report dentro do boundary é aceito
```

## AC-4: RLS deny-by-default e isolamento por município
```gherkin
Given RLS habilitado em todas as tabelas de `public`
When consulto qualquer tabela como `anon`
Then nenhuma linha é retornada e inserts/updates/deletes falham
When um usuário `agent` do município A consulta report/risk_area/alert/inspection
Then vê apenas linhas do município A, nunca do município B
When um usuário autenticado sem linha em `profile`
Then não vê nenhuma linha de domínio
When qualquer usuário autenticado tenta alterar o próprio `profile.role` ou `municipality_id`
Then a operação falha (sem escalonamento de privilégio)
<!-- audit-added -->
When um usuário `agent`/`surveillance`/`admin` tenta INSERT, UPDATE ou DELETE em qualquer tabela de domínio
Then a operação falha ou afeta 0 linhas
```

## AC-7: Higiene de privilégios (defesa em profundidade além do RLS)

## AC-8: Integridade fail-closed e trilha preservada
```gherkin
Given o trigger espacial de report
When o insert é feito por um role que não enxerga `municipality` (RLS) ou com `municipality_id` inexistente
Then o insert é rejeitado (nunca aceito por ausência de boundary)
When tento apagar um report que tem inspection
Then a exclusão é bloqueada (histórico de inspeção não some em cascata)
When uma inspection referencia um agent de outro município, ou um alert é reconhecido por profile de outro município
Then a operação é rejeitada pela FK composta de tenant
```
